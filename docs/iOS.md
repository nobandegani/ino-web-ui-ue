# iOS

InoWebUI on iOS runs through `WKWebView`, the same engine Safari uses
since iOS 8. The implementation mirrors the Android impl in shape — same
contract, same lockdown rules, same `bridge.js` payload — but lives in
Objective-C++ and integrates with UE's iOS app delegate.

## How it works

```
UE game thread (C++)
     |
     |   dispatch_async(dispatch_get_main_queue(), ^{ ... })
     v
iOS main thread (Objective-C++)
     v
WKWebView
     - sibling subview of [IOSAppDelegate GetDelegate].RootView
     - added ABOVE FIOSView (the Metal-layer game surface)
     - transparent background -> UE scene shows through
```

Public C++ entry points run on the game thread. `WKWebView` is
main-thread-only, so each one marshals its real work onto the iOS main
queue. `Initialize` uses `dispatch_sync` so `IsReady()` is true by the
time the call returns. Delegate callbacks fire on main and marshal back
to the game thread via `AsyncTask(ENamedThreads::GameThread, ...)` — the
same `DispatchOnGameThread<Lambda>` shape as the Android impl.

## Runtime architecture

A single `InoWebViewBridge_iOS` Objective-C class hosts every callback
we care about:

- `<WKScriptMessageHandler>` — JS -> native bridge.
- `<WKNavigationDelegate>` — `decidePolicyForNavigationAction:` for
  lockdown, `didFinishNavigation:` / `didFailNavigation:` /
  `didFailProvisionalNavigation:` for `OnNavigationCompleted`,
  `webViewWebContentProcessDidTerminate:` for `OnProcessFailed`.
- `<WKUIDelegate>` — `runJavaScriptAlertPanel...:` /
  `runJavaScriptConfirmPanel...:` / `runJavaScriptTextInputPanel...:`
  for dialog suppression, `createWebViewWithConfiguration:...` for
  `window.open` blocking.

Plus an `InoWebViewSchemeHandler_iOS` (`<WKURLSchemeHandler>`) that
serves `inoweb://<host>/<path>` requests from a local folder — the iOS
equivalent of WebView2's `SetVirtualHostNameToFolderMapping` and
Android's `WebViewClient.shouldInterceptRequest`.

## JS bridge

Same `window.InoWebUI.send / .on / .off / .once` API as every other
platform. Detection inside `bridge.js` is by transport object:

- Windows: `window.chrome.webview`.
- iOS: `window.webkit.messageHandlers._InoWebUIHost`.
- Android: `window._InoWebUIHost` (added via `addJavascriptInterface`).

The iOS host name (`_InoWebUIHost`) sits under
`window.webkit.messageHandlers`, so it does NOT collide with the
Android global of the same name. JS user code never has to care — the
shim abstracts it.

## Virtual host: the `inoweb://` scheme

`WKWebView` does not expose a `SetVirtualHostNameToFolderMapping`
equivalent and does NOT allow intercepting `https://` requests
(security policy). The plugin works around this with a custom URL
scheme:

- Configure `VirtualHostName` and `VirtualHostFolder` exactly as on the
  other platforms.
- The plugin registers a `WKURLSchemeHandler` for the `inoweb` scheme
  and translates each request into a local-file read.

### Cross-platform config — no `#if PLATFORM_IOS` needed

Pass your `InitialURL` (and any later `LoadURL` / `LoadURLWithHeaders` /
`LoadHTMLString` base URI) using the canonical `https://<vhost>/...`
form you already use on Win64 and Android. The iOS impl auto-rewrites
`http://<vhost>/...` and `https://<vhost>/...` to `inoweb://<vhost>/...`
at the navigation boundary — host has to match the configured
`VirtualHostName` exactly (case-insensitive whole-host); other URLs pass
through untouched. So this works on every platform with one config:

```cpp
Config.InitialURL        = TEXT("https://my-ui.local/index.html");
Config.VirtualHostName   = TEXT("my-ui.local");
Config.VirtualHostFolder = TEXT("WebUI/dist");
```

You can still pass `inoweb://my-ui.local/index.html` explicitly if you
prefer — the rewrite is a no-op on URLs that already use the custom
scheme.

The `bLockToVirtualHost` lockdown rule on iOS allows the `inoweb:`
scheme as an internal scheme (always passes), in addition to whole-host
matching against `VirtualHostName` for any URL.

## Audio mute (`SetMuted` / `bStartMuted`) — partial

`WKWebView` has no first-class audio-mute API. The plugin's iOS impl
walks every `<audio>` and `<video>` element in the page via injected JS
and toggles `.muted` — the closest cross-platform-symmetric behaviour
we can synthesise.

Caveats:

- Media added to the DOM AFTER the call won't pick up the muted state.
- AudioContext / Web Audio output is not affected.
- The whole-app `AVAudioSession` mute switch is not toggled (and
  shouldn't be — that would silence the game too).

If you need strict app-level audio control on iOS, do it from your
game's audio-session config rather than going through `SetMuted`.

## DevTools

There is no in-process DevTools on iOS — Apple does not ship one.
`UInoWebView::OpenDevTools()` logs the workflow:

1. On the iOS device: Settings -> Safari -> Advanced ->
   **Web Inspector** on.
2. On the Mac: Safari -> Settings -> Advanced ->
   **Show features for web developers** on.
3. Connect the device via USB and trust the computer.
4. In Safari on the Mac: **Develop -> \<DeviceName\> -> \<Your WebView page\>**.

You'll get the full Safari Web Inspector against the live page.

The floating dev-tools overlay (the round wrench button) does work on
iOS — it's just JS, gated by the same `bEnableDevTools` flag as the
other platforms.

## Bounds and density

UE reports bounds in screen pixels. UIKit takes points. The iOS impl
divides by `[UIScreen mainScreen].scale` to convert pixels to points,
mirroring how Android multiplies by `displayMetrics.density` going the
other way.

In **auto-bounds mode** (default), the plugin sets
`UIViewAutoresizingFlexibleWidth | UIViewAutoresizingFlexibleHeight`
and re-syncs `frame = parent.bounds` on every `SyncBounds` call, so
orientation changes and split-view resizes are picked up natively.

In **manual-bounds mode** (after `UInoWebView::SetBounds(X,Y,W,H)`),
autoresizing is dropped and `SyncBounds` applies the supplied rect
verbatim (with the pixel-to-point conversion). Switch back to auto with
`UInoWebView::SetBoundsAuto()`.

## Build setup

Nothing exotic. The `iOS` branch in `InoWebUI.Build.cs` adds the
required Apple frameworks:

```csharp
PublicFrameworks.AddRange(new string[]
{
    "WebKit",
    "UIKit",
    "Foundation",
});
PrivateDependencyModuleNames.Add("Launch");  // [IOSAppDelegate GetDelegate]
```

No UPL/IPL injection is needed — `WKWebView` requires no
Info.plist additions for inline display. (If your page hits arbitrary
HTTP origins, App Transport Security exceptions are still your project's
call to add.)

## Troubleshooting

- **Page never loads, log says "host mismatch" or "file not found".**
  Check that `Config.InitialURL` uses the `inoweb://` scheme on iOS, and
  that `VirtualHostFolder` resolves to a real directory.
  `FPaths::ConvertRelativePathToFull` is applied automatically.
- **WKWebView renders but DevTools stays empty in Safari.** Make sure
  Web Inspector is enabled on the device (Settings -> Safari ->
  Advanced) AND your Mac's Safari has the Develop menu enabled.
  Connecting via USB sometimes also requires the iOS device to trust
  the computer.
- **Transparent background isn't working.** `bTransparentBackground` is
  applied to both `webView.opaque` and the underlying `scrollView`'s
  background colour. If your HTML has its own background colour, that
  paints on top — set `body { background: transparent; }` in CSS.
